# Generation admission and outbox

This slice admits a five-second text-to-video request atomically. API-next exposes gated v2 quote/admission/read endpoints; admission remains closed in the production composition. Apps/worker now runs the Temporal dispatcher, durable control flow, and submission/polling activities. Media publication remains unwired, so workflows wait at awaiting_media rather than claiming a published result.

`services.generation.create` takes an authenticated internal `userId`, a user-scoped `requestKey`, prompt, `480p|720p`, aspect ratio, and exactly five seconds. It rejects extra input properties, including external image URLs. The composition layer locks identity, checks request replay, reserves credits, and writes one job and one `generation.requested` event in one transaction. The estimate comes from `estimateCreditsFor`; the internal estimated cost is the selling price divided by two and rounded up, following the current pricing contract. This is an estimate derived from pricing, not a supplier quote or reported cost.

Matching replay returns the stored job even after completion; changed request content conflicts. Creation still requires an active identity. `get` requires the owning user ID. Completion/failure lock the job before its wallet and atomically settle/refund and write the terminal state. Matching terminal replay is idempotent; changed or opposite terminal outcomes conflict. An account becoming inactive does not strand its already accepted job. Actual supplier cost remains null when unknown.

`complete` accepts an opaque internal `outputRef`, not an externally fetchable URL. There is no asset table or permission/AI-label validation in this slice, and this reference must not be exposed as a downloadable result. Future workers must pass only validated internal assets when that capability exists.

`services.generationOutbox.claim` leases one event for 30 seconds with `FOR UPDATE SKIP LOCKED`. Reclaiming an expired lease generates a new random token. `ack` and `release` lock the event before checking the token and database time. A delivery that waits for a lock until after expiry cannot acknowledge it. `release` delays the next attempt by exponential backoff, capped at 300 seconds. No process clock participates in lease ownership.

The future dispatcher must call the workflow service outside the database transaction, start using the stable `generation:<jobId>` workflow ID, and only acknowledge after confirmed acceptance. Temporal start must reject reuse of a closed workflow ID (`WorkflowIdReusePolicy.REJECT_DUPLICATE`); a stable ID alone does not prevent a previously closed workflow from being started again. A crash between workflow acceptance and acknowledgement can redeliver. Activities can also replay or retry and must independently enforce idempotency at every side-effect boundary. These rules do not promise exactly-once provider execution. The workflow must load the job and honor an already terminal state before calling a provider. Provider acceptance ambiguity, real worker recovery, asset ownership, media processing, and publication remain separate work.

The generation tests use an explicit loopback `workbench_audit*`/`workbench_verify*` database. They create random users and scoped failure triggers, exercise 50-way admission/completion/claim races, and remove their fault triggers. They never truncate tables or connect to production.

`services.providerSubmissions` records a single durable submit claim per job before external IO. Only the first caller receives its token; later calls never reclaim a submitting/unknown operation. Accepted receipts bind the provider task ID; matching receipts replay, different IDs conflict, and a late original receipt can resolve unknown. Definite rejection records rejection/job failure/refund in one transaction. This avoids blind retries but does not guarantee automatic recovery of ambiguous acceptance; operations for reconciliation are still required. See ADR-0007.

Outbox integration tests now create a dedicated random test database because claim consumes the entire queue. This prevents fixtures from parallel API/worker tests being acknowledged by another suite. The database is migrated and dropped only by its owning suite; the root verifier's temporary PostgreSQL container remains the outer cleanup boundary.
