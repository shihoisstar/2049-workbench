# ADR-0004:前端技术栈 = Taro + React + TypeScript;UI 走组件库拼装路线

- 状态:**已定稿**(2026-10-03,产品负责人拍板 Taro+React+TS+NutUI;证据见 `技术确认会-证据包.md`)。协作模型:产品/架构/商业层决策由产品负责人+AI 搭档定,搭档对实现层保留异议权(随时改 ADR)
- 关联:ADR-0002(渠道)、ADR-0003(架构)

## 决策一:Taro(React + TS)胜出 uni-app

| 维度 | Taro(React)+TS | uni-app(Vue) | 权重 |
| --- | --- | --- | --- |
| 语言统一 | 全项目单一 TS(后端 NestJS/契约 Zod/前端 React) | Vue 体系,与 TS 后端两套心智 | 高 |
| AI 语料 | React 训练语料显著多于 Vue,Agent 产出质量与返工率直接受益 | 够用 | **最高(团队后端主力+AI 协同)** |
| 双端 | weapp+H5 一码双出(匹配 ADR-0002 渠道) | 同样支持 | 高 |
| 维护与配套 | 京东维护;NutUI(电商基因组件库) | DCloud;HBuilderX 工具链偏锁定 | 中 |
| 团队现状 | 无前端老手,靠 AI+组件库 → React 生态答案最多 | 更适合已有 Vue 老手 | 高 |

配套组件库:**NutUI-React-Taro 定稿**(2026-10-03 证据:它是唯一有官方 Taro-React 支持的主流组件库,周下载 8,168、最新版 2026-09-03;TDesign 无官方 Taro 方案——tdesign-miniprogram 为原生 WXML、tdesign-taro 为占位空包;详见 `技术确认会-证据包.md`)。

## 决策二:UI/UX 工作流(无设计师团队)

> **修订(2026-10-03,负责人定调)**:对标 29 张截图是**布局与交互**的规格——复刻的是"这个 APP 怎么组织页面与流程";**视觉风格走自有体系,定调"黑红商业化"**(近黑 hero + 品牌红渐变 CTA,与 NutUI 默认红天然一致、组件零覆写),tokens 见 `apps/miniapp/src/styles/tokens.scss`(v1 基线;换肤只改该文件)。结构对标 + 风格自持,两者并行不悖。

原则:**不设计,只组装;不发明交互**。对标 29 张截图 = UI 规格;创新只花在差异化点(积分估算条/失败退积分提示/诚实营销)。

1. **组件库先行**:装 NutUI/TDesign,定 design tokens(主色/8px 网格/圆角/字号阶梯);UI=组装现成组件
2. **低保真=截图标注**:对标截图逐屏标注"保留/改掉/换成我们的",写进 `docs/specs/`(这是需求评审,不是设计)
3. **Figma/即时设计只做拼装(可选)**:导入组件库官方 Kit + 对标截图拼 6 个关键屏;跳过直接写代码也成立
4. **AI 生成页面**:规格=对标截图+组件库文档 → Agent 产 Taro React 页面 → 人 review → 真机迭代

V1 关键屏(共 6):模板 feed 首页 / 创作表单(含积分估算条)/ 生成进度(状态机可视化+失败退积分)/ 作品详情+下载 / 我的(积分+账单明细)/ 充值+登录授权。

## 后果与护栏

- 正面:单一语言全栈;Agent 友好;组件现成;UI 成本压到最低
- 风险:Taro 编译层偶有小程序差异坑(主流问题,社区答案多);H5 端支付跳转(微信 H5 支付需外跳)按 ADR-0002 兜底方案处理
- 护栏:不自研通用组件(先用组件库);不引 CSS-in-JS 花活(用 Tailwind 或组件库样式体系其一);设计 tokens 进代码库由契约层共享
