# ADR-0003:Agent 时代架构原则与技术形态

- 状态:已接受(2026-10-02)
- 触发:产品负责人要求"2026 最优雅架构、前后端完全分离、支撑未来超级智能 Agent 并行协同极速开发、教科书级 Agent 时代架构、新技术全用上"

## 背景与关键认知(先立原则,再选技术)

产品负责人的要求中,一半直接采纳,一半必须纠正:

**采纳**:面向 Agent 并行开发的架构是真问题,而且有明确答案——**契约驱动 + 边界严格 + 验证自动化**。所谓"教科书级"的定义是:任何人或任何 Agent,只读 `contracts/` 和各包 `AGENTS.md`,就能正确提交一个功能;一个 PR 能否合入完全由机器门禁判定,Agent 不可能假装完成。

**纠正**:"牛逼的新技术全部用"恰恰违背这个目标。模型对**主流、文档丰富、训练语料深**的技术栈产出质量最高;最新框架 = 训练语料薄 = Agent 幻觉多、返工多。模型越强(GPT-6/未来更高智能),清晰契约的价值越大(可自服务),隐性约定的价值越小(没人能懂)。**创新预算应该花在 Agent 工作流(规格、门禁、MCP)上,而不是框架猎奇上。**

## 决策

### 1. Monorepo 结构(pnpm workspaces + Turborepo)

```
workbench/
├─ apps/
│  ├─ miniapp/      # 微信小程序(uni-app/Taro,搭档技术确认二选一)
│  ├─ h5/           # H5:充值兜底 + 落地页(与小程序共享业务层)
│  ├─ admin/        # 运营后台(React,轻量)
│  └─ api/          # 后端(Fastify 模块化单体;2026-10-03 修订见文末)
├─ packages/
│  ├─ contracts/    # ★唯一接口事实源:Zod schema → 自动生成 OpenAPI + TS 类型 + JSON Schema
│  ├─ domain/       # 纯业务规则:状态机/计费/剧本解析器(零框架依赖,双端复用)
│  └─ shared/       # 常量与工具
├─ infra/           # docker-compose 起步(不上 K8s)
├─ docs/            # ADR / specs/ (每个需求一份规格) / 架构图(archify)
└─ AGENTS.md        # 根级 + 各包级:Agent 开发规范(命名/分层/禁止事项)
```

### 2. 契约驱动(前后端完全分离的实现方式)

- `packages/contracts` 是**唯一**接口事实源:改契约 = 改一处,OpenAPI 文档、前端类型客户端、JSON Schema(生成任务/剧本格式)全部自动再生成;
- 契约变更必须走 PR;破坏性变更必须挂 ADR;
- 前端不允许手写后端类型,后端不允许绕过 schema 收发数据。

### 3. 验证门禁(并行协同的信任机制)

CI = lint + typecheck + unit + **contract-diff 检查** + e2e。任何提交(人写的或 Agent 写的)过不全部门禁不得合入。这是"多 Agent 并行不互相破坏"的唯一保障。

### 4. 规格驱动工作流

每个功能 = `docs/specs/<需求ID>.md`(目标+验收标准+契约 diff)→ 人或 Agent 认领 → 实现 → 门禁 → 人工验收。需求池 ID 即规格 ID,一一对应。

### 5. 技术选型(主流稳定栈)

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 后端 | Fastify 模块化单体(非微服务;原 NestJS,2026-10-03 修订见文末) | 2 人团队,模块边界清晰即可;微服务是分布式税 |
| 数据库 | PostgreSQL + Drizzle(类型安全) | 主流、Agent 训练语料深 |
| 任务队列 | Redis + BullMQ(状态机按镜序 §12) | 够用;Temporal 是未来选项不进 V0 |
| 存储 | S3 兼容(阿里 OSS/腾讯 COS) | 国内合规 |
| 合成 | FFmpeg worker 容器 | 行业标准 |
| 可观测 | 结构化 JSON 日志 + request-id + 成本账本事件 | 账本三分照镜序 §10.8 |
| Agent 运维接口 | MCP 工具服务(部署/日志/迁移) | 为未来 Agent 自主运维留口,不是噱头 |

## 护栏(反猎奇清单)

1. 不用微服务、不上 K8s、不用 GraphQL(REST+OpenAPI 对 Agent 更友好)、不引 Temporal;
2. 主链路只允许"LTS + 训练语料深"的技术;实验性技术只进 sandbox 分支,验证后按 ADR 引入;
3. 每引入一个新依赖,`packages/contracts` 和 AGENTS.md 同步更新——否则门禁不过;
4. "支撑未来更智能的模型"的正确姿势 = 任务切得足够小 + 契约足够清楚 + 验证足够自动,而不是预设某个模型的能力。

## 修订记录

- **v1.1(2026-10-03)后端框架 NestJS → Fastify**。原因:启动 T1.1 时核对参考实现 `2049-agent/apps/server`,其实际栈为 Fastify + @fastify/jwt + Zod(扁平模块);复用评估中的网关/计费移植(T1.2/T2.1)零转换的前提是同框架。代价评估:NestJS 的 DI/装饰器对单人+AI 是纯样板税,且与我们 Zod 契约直连需额外管道;Fastify 主流度与训练语料同样深,`app.inject` 原生测试无需 supertest。原则不变:仍是模块化单体、非微服务。
