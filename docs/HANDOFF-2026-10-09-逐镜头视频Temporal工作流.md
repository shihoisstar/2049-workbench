- workflow ID 固定 `drama-video:<jobId>`。

### 4.2 mock 视频活动

文件：`apps/worker/src/shot-video.ts`。

它不是走 `https://mock.invalid/...` 下载路径。原因：mock provider 的 URL 不可下载，而且 mock 链路必须运行时零外部依赖。

`MOCK_MP4` 是内联 base64 解码的 MP4：

- 3904 bytes；
- H.264；
- `240 × 426`；
- `5000ms`；
- 无音轨；
- 画面已烧录 `AI生成 · 2049出片`；
- MP4 comment metadata 是 `AI generated by 2049出片`；
- sha256 是 `ba210c83633927c8d5622c3f96de26c349af074d1b85673f82847a6f07fea3cd`。

三个 activity：

- `createShotVideoSubmissionActivity`：幂等 claim + receipt，provider key 为 `mock-shot-video:v1`；
- `createShotVideoPublishingActivity`：put MP4 → `dramaShotVideoAssets.publish`；

## 5. `verify-runtime.cjs` 的变化与运行顺序（易踩坑）

文件：`apps/worker/scripts/verify-runtime.cjs`。

新增 shot-video runtime 场景时，有一个刻意的时序：

1. 先让 candidate image workflow 成功；
2. `selectCandidate`；
3. 创建 shot video job；
4. 临时停 live worker；
5. 人为让第一次 outbox `ack` 抛错，得到 `capturedShotVideo`；
6. 启动新 worker，验证 redelivery 是同一个 Temporal run，且成功发布；
7. 验证已结束 workflow 的 requested/resume 事件不重启；
8. 之后停 Garage，构造一个已发布 candidate image 的 shot video job，验证发布失败退款。

**不要将 Garage 停止提前。** 成功发布场景需 S3；outage 场景才需要停止它。

**不要在 live worker 工作时自己抢 outbox 来“帮助测试”。** 这是竞态源；脚本中的说明和时序就是为了保证唯一 claimer。

所有 evidence 通过 `save()` 写到 `docs/验收留档/...`，该函数会写后读回校验，符合 `AGENTS.md` 的 D 盘写后读回纪律。
