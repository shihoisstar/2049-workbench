# ADR-0005：营销视频与漫剧双流水线重建

- 日期：2026-10-06
- 状态：重建方向已确定；首轮审计与隔离验证基础设施完成，业务重建尚未完成。
- 授权：负责人要求重新评估技术栈并重建，明确首版同时交付微信小程序、H5、营销视频和漫剧核心闭环。
- 替代范围：ADR-0003 的后端组织、工作流禁用约束，以及 ADR-0004 的“只组装、不设计”和绑定 NutUI 的约束。历史文档保留作为决策记录，不再约束新实现。
- 不改变：产品品牌、积分不变量、数据所有权、合规要求、负责人确认后才执行 Git 提交。

## 1. 为什么重建

当前实现能够编译和完成部分正常业务链路，但不能据此推出它已具备生产可靠性或适合多 Agent 并行扩展。

独立数据库中的三项探针已复现：

| 操作 | 正确行为 | 当前实际行为 |
| --- | --- | --- |
| 100 积分，预留 50、退款、再结算 30 | 拒绝结算，余额 100 | 余额 120 |
| 100 积分，两笔不同业务键各入账 10 | 余额和流水均为 120 | 余额 110，流水 120 |
| 100 积分，两笔不同业务键各预留 80 | 仅一笔成功，余额 20 | 两笔成功，余额 20，流水 -60 |

这证明现有测试没有封住钱包竞争路径。另有任务与计费跨事务、终态后补账不可恢复、生图依赖 HTTP 长轮询等静态可达风险，详见 [审计记录](重建审计-2026-10-06.md)。

现有 `pnpm gate` 实测执行 29 个任务、54 个真实测试、两端构建，缓存命中 0；这些问题依然存在。重建的目标是补齐验证范围和业务模型，不是把旧门禁全绿当成完成证明。

Fastify、PostgreSQL、Drizzle、Taro 并非上述错误的必然原因。选择新的组织方式必须有具体收益，保留一个工具也必须重新论证，不能以“旧项目用了”为理由。

## 2. 产品与部署边界

第一版交付两个创作闭环：

1. 营销：素材/描述 → 文案辅助 → 报价 → 预留积分 → 生成 → 标识处理 → 成片下载。
2. 漫剧：想法或已有剧本 → 剧本版本 → 角色/场景确认 → 分镜候选 → 逐镜头生成 → 配音/字幕/合成 → 导出版本。

微信小程序与移动 H5 使用同一 Taro 应用。H5 对桌面宽度做适配，但本期不新增专业多轨桌面编辑器。运营后台是独立 Web 客户端，在有实际管理用例时建设，不用空壳冒充交付。

前后端完全分离指：独立构建、独立部署、独立配置、通过版本化 HTTP API 交互。一个 monorepo 和一个业务数据库不破坏这个边界。前端不得 import 服务端业务、ORM schema、密钥配置或 worker 源码。

## 3. 技术选择与代价

| 层 | 目标选择 | 选择理由与代价 |
| --- | --- | --- |
| 运行时 | Node.js 24 LTS、TypeScript strict | 同一语言贯穿应用。固定版本；禁止自动追随浮动 latest |
| 工作区 | pnpm workspace + Turborepo | 依赖图、增量构建继续适用；集成测试不可依赖缓存证明环境正确 |
| API | NestJS + Fastify adapter，模块化单体 | 固定 controller/use-case/provider 装配方式，降低 Agent 自由发挥；增加 DI/装饰器与适配器维护，不能替代数据库正确性 |
| 数据 | PostgreSQL + Drizzle + 审查后的 SQL migrations | 事务、约束和查询计划可直接审查。目标评估 PostgreSQL 18 稳定线；旧 16 库不原地升级，不因版本较旧就判定数据库不适用 |
| 长任务 | Temporal TypeScript 持久工作流，先执行恢复验证 | 漫剧包含等待用户确认、镜头并行、候选选择和跨进程恢复。引入独立服务、工作流确定性及版本管理成本，必须证明收益再进入业务主链路 |
| 缓存/限流 | Redis，只用于明确需要的缓存、分布式限流 | 余额、已受理任务、角色版本不能只存在 Redis；不能形成第二个业务事实源 |
| 素材 | S3 兼容对象存储 + PostgreSQL 资产元数据 | 业务保存 assetId，不依赖供应商临时 URL；增加签名 URL、访问授权和生命周期测试 |
| 媒体处理 | 独立媒体 worker + FFmpeg | CPU/内存消耗与 HTTP 服务隔离；输入/资源限额、进程超时和临时文件清理要验收 |
| 移动前端 | Taro + React + TypeScript，按功能重写页面 | 已确认的 12 屏可用该技术表达；没有证据证明换 Vue 能解决当前业务与视觉缺陷。React 版本服从 Taro 兼容矩阵 |
| UI | 自有 design tokens + 少量基础组件 | 认可的暖白、炭黑、朱红方向是视觉依据。组件库是实现选择，不再决定产品外观；代价是维护基础组件状态和双端验证 |
| 契约 | Zod 唯一源 → 完整 OpenAPI → 生成式客户端 | 服务端运行时校验；前端使用生成操作与可注入 transport。新增生成和兼容性检查，禁止手写第二套 DTO |
| 验证/观测 | 单元、隔离集成、H5 流程、小程序实际运行；结构化日志和 OpenTelemetry | 前后端、请求、作业、模型调用和账本用 ID 关联；敏感内容不进入普通日志 |

2026-10-06 npm 查询得到 NestJS 12.1.2、Taro 4.3.0、Drizzle 0.45.3、Temporal worker 1.24.0。它们是核对时的候选版本，不代表已经安装、兼容性已验证或已经替换现网。实际使用版本由安装后的锁文件和兼容性验证共同确定。

### 比较过的替代路线

- Fastify 原地重组可以修复全部已发现事务缺陷，成本更低。选择 NestJS 是为新业务与并行贡献者提供统一装配方式，不声称 Fastify 性能或能力不足。
- BullMQ + 数据库 outbox + 幂等消费者也能实现可靠生成。Temporal 的新增价值必须由“等待确认后恢复、单镜重试、部署版本兼容”证明；若验证失败，记录新的 ADR，采用前者，而不是悄悄维护两套编排权威。
- Nx 可执行依赖标签约束，但当前不必同时更换构建工具。先用依赖规则/架构测试封住边界，图规模或 affected 工作流出现实证瓶颈时再评估 Nx。
- 独立 React Web 工作台适合复杂桌面交互，但本期用户选择微信小程序 + H5，不增加第二套面向用户的 UI。
- 微服务、Kubernetes、多数据库、事件溯源全家桶不因“Agent 时代”自动引入。并行开发规模不等于线上分布式服务规模。

## 4. 目标目录和依赖方向

以下是目标结构，不是对当前目录的完成声明。只在功能实施时建立必要文件，不批量生成空模块。

```text
apps/
  api/                 HTTP 入口、鉴权、配置与依赖装配
  worker/              workflow 与 activities 装配
  media-worker/        FFmpeg activities 与资源限制
  miniapp/             Taro 页面与平台适配
  admin/               有明确运营用例后建设
packages/
  contracts/           API/event schema 与错误语义
  api-client/          生成的操作、类型与 transport 接口
  server/              仅服务端可依赖的业务模块
    src/modules/
      identity/
      billing/
      assets/
      generation/
      drama/
  model-gateway/       供应商协议、能力与调用适配
  design-tokens/       品牌与布局变量，不进入 API 契约
infra/                 本地隔离环境与部署定义
scripts/               生成、验证、数据演练
docs/specs/            规格、依赖、验收与任务可写范围
```

每个服务端模块拥有 `public.ts`、用例、数据访问和必要的纯业务规则；复杂度需要时再分 domain/application/infrastructure。禁止为每个 CRUD 强建四层空目录。其他模块只能通过 public API 调用，不直接 import 对方 repository/schema。

允许：miniapp → api-client → contracts；api/worker → server public API；generation → model-gateway。禁止：miniapp → server、app → 另一个 app 的实现、领域纯规则 → IO、模块之间深路径访问。

跨模块事务由组合用例建立工作单元，对外提供在同一事务内绑定的业务操作，例如 billing.reserve 和 generation.create。原始 Drizzle tx 只存在于持久化装配层，不作为模块公开参数或返回值；不得暴露 repository、schema 或任意 SQL 执行器。导入门禁拒绝深路径访问，额外规则拒绝持久化层之外的 raw SQL，SQL 表归属由审查与集成测试核验。这是代码组织约束，不冒称单一数据库账号形成数据库级权限隔离。迁移生成由单一集成人串行处理，不让每个 Agent 修改聚合迁移日志。

## 5. 数据与可靠性设计

### 5.1 唯一所有者

| 模块 | 拥有的数据 | 对外能力 |
| --- | --- | --- |
| identity | 用户、平台身份、会话、注销状态 | 身份解析、访问主体、会话撤销 |
| billing | 钱包、不可变流水、预留、报价、订单、支付事件 | 报价、预留、互斥结算/退款、对账 |
| assets | 原始素材、派生素材、校验和、归属、到期时间、审核与标识状态 | 授权读写、引用、发布和清理 |
| generation | 作业、供应商尝试、受理凭据、重试/恢复信息 | 创建/查询/重试/取消支持范围、最终计费 |
| drama | 项目、剧集、剧本版本、角色版本、镜头、候选选择、导出版本 | 项目工作流、版本引用、单镜重做和导出 |

身份不能把可自行提交的 deviceId 当长期账户凭据。小程序登录与 H5 游客能力分别定义会话安全，服务端执行所有权验证；前端隐藏按钮不能代替权限。

### 5.2 一次受理的事务

请求携带用户范围内的幂等键和报价版本。数据库同一事务写入：幂等请求记录、作业、积分预留和 outbox。幂等键相同但 payload 不同返回冲突。响应成功后，用户必须能够查询已受理作业。

outbox 的投递是至少一次，消费者按业务键去重。Temporal workflowId 由作业 ID 推导；outbox 重投不能创建第二笔收费工作流。外部模型接受幂等键时传稳定标识；不支持时，响应丢失进入待对账/未知受理状态，不盲目再次付费提交。

### 5.3 钱包与任务终结

钱包更新使用行锁或条件原子更新，数据库同时约束非负余额。一次预留只能终结为 settled 或 refunded。流水保持不可变；补偿写新记录，不改旧金额。

任务终态、预留终结和最终流水在同一个业务事务内完成。任何重放返回同一终结结果。跨作业并发对同一钱包执行时，也必须满足余额等于流水和。

计价区分用户积分、成本估算和上游实报成本；供应商未返回真实成本时标为未知，不拿积分估算伪装实报。客户报价变更不会改变已受理任务的计价版本。

### 5.4 编排与业务状态

Temporal 管理工作流控制流、等待、定时器和 activity 重试；PostgreSQL 管理业务实体、资产与账本。前端读取持久业务视图。明确投影延迟与补偿，不在 BullMQ 和 Temporal 同时维护同一条流程。

workflow 中禁止直接数据库/网络 IO，activities 才能调用模块能力。activities 按至少一次执行设计。工作流升级必须做旧历史 replay/版本兼容检查。

独立镜头 generation job 失败只影响该镜头 attempt；旧成功候选保留。导出引用确定的剧本版本、角色版本、候选集合、配音/字幕版本及素材哈希，不引用“最新镜头”这种会变化的含义。

没有正确 AI 标识的成片不能发布。媒体处理失败进入可重试失败/退款路径，不静默原片直出。对象存储记录与上传/删除分布式边界采用状态记录、幂等操作和定期对账；不声称跨数据库/S3 存在原子事务。

## 6. Agent 协作协议

面向能力增强的 Agent，稳定接口是任务规格与工具协议，不是模型品牌或提示词角色扮演。开发 Agent 与产品内生成工作流是两种系统，不能混为一谈。

每份任务包含：需求 ID、输入契约、可写路径、依赖任务、禁止改动、验收命令、失败场景、交接证据。契约、lockfile 和数据库迁移有单一集成人。其他 Agent 可提变更建议，但不在各自分支同时重写共同基础。

并行单位是边界明确的功能切片。每个 Agent 使用独立 worktree、数据库、队列/工作流命名空间、素材前缀和端口。禁止共享测试库、全局 flushdb、读取生产密钥作为默认开发条件。

实施顺序：每个纵向切片先合并它需要的契约，再让客户端、用例和适配器并行；不要求全部漫剧契约一次定型。完成后独立审查与集成验证。测试独立不等于 Git 分支已隔离，当前基础脚本只解决环境隔离，不能宣称完整协作系统已经建立。

Agent 可自主执行本地可逆开发、模拟供应商、故障注入、回归测试；Git 提交、公开发布、真实支付、破坏性数据迁移按既有授权边界执行。此 ADR 不授予生产管理凭据或新的外部通信权限。

## 7. 完成标准

1. 两个 Agent 在独立 worktree 同时验证，不共享数据库或队列；退出后清理各自资源。
2. 前端 import 后端、模块深路径跨界、领域引入 IO 三类反例均使架构检查非零退出。
3. 请求/响应约束变化能触发完整 schema 漂移；生成客户端可重复；破坏性兼容检查与快照重签分离。
4. 钱包 50 路竞争、同幂等键重复提交、settle/refund 竞争均保持不变量。
5. 在数据库提交、工作流启动、上游受理、媒体处理、最终结算边界中止进程，恢复后不重复扣费、不吞掉受理任务。
6. 营销链路与一集漫剧端到端完成；单镜失败只重做该镜，导出引用可追溯。
7. 已认可 12 屏有加载、空、失败、权限、过期等状态；H5 流程与视觉验证、小程序实际运行分别留证。
8. 全新环境可迁移、启动、验证；数据迁移有备份、账本核对、回滚演练。真实支付和资质仍有独立上线门槛。

## 8. 实施顺序与切换

2026-10-06实施落点：新入口暂放apps/api-next（@wb/api-next，默认3011），旧apps/api与部署保留作为基线；新业务模块迁移、恢复验收及切换演练完成后再替换旧入口并移除过渡命名。新入口当前只有基础探测，不能用于承接旧业务请求。UI直接依据已认可参考图实现，Figma不作为强制前置。

详见 [重建执行规格](specs/REBUILD-01-双流水线重建.md)。先锁定可复现缺陷、隔离环境及契约，再做新身份/账本/任务纵向切片，然后并行营销 UI 和漫剧模块，最后验证合成、双端与切换。

不删除旧仓库、不重置数据、不覆盖现有可运行部署。新实现使用独立环境。旧未结束任务有明确 drain/继续查询/退款策略；新旧 worker 绝不消费同一任务。完成数据与产物核对后才切换入口。

切换前可恢复到演练确认的旧快照。切换后如果已经产生新订单、账本或作业，禁止仅回切入口或恢复旧备份：先暂停相关写入，对新写入做对账和兼容迁移，能够无损读取时才回切；否则保持新库并前向修复。R4.2必须实际创建切换后订单/作业并验证处置，不承诺任意时点一键回滚。

## 9. 核对的官方资料

- [NestJS 模块封装](https://docs.nestjs.com/modules)：模块默认封装 provider，公开 exports 构成服务接口。
- [NestJS Fastify adapter](https://docs.nestjs.com/techniques/performance)：平台专用插件仍需兼容性验证。
- [PostgreSQL 事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)：默认隔离并不自动避免所有业务竞争；需要正确锁与条件更新。
- [Drizzle transactions](https://orm.drizzle.team/docs/transactions)：事务工具不是业务正确性的替代品。
- [Temporal TypeScript](https://docs.temporal.io/develop/typescript)、[工作流执行](https://docs.temporal.io/workflow-execution)：作为持久工作流验证依据。
- [Taro 介绍](https://docs.taro.zone/docs/)：React 与多端编译能力。
- [OpenAPI TypeScript](https://openapi-ts.dev/introduction)：候选客户端类型生成工具，具体生成链需验证 Taro transport。
- [dependency-cruiser](https://github.com/sverweij/dependency-cruiser)、[Nx boundaries](https://nx.dev/docs/features/enforce-module-boundaries)：依赖约束方案比较。

这些资料支持技术能力，不构成“市场最优”或“未来模型一定擅长”的证据。
