## 二、方法论蒸馏(12 条,按需求生命周期组织)

### 总纲:一条主流程

```
接收需求 → 需求池管理 → 分析(辨真伪) → 排优先级 → 梳理拆分 → 需求设计
→ 需求评审(先业务后开发) → 修改文档 → 开发(沟通+记录) → 测试(用例对齐)
→ 产品验收(对照文档) → 上线(回归测试) → 记录优化点 → 下一轮迭代
```

### 1. 需求池:一切从"接住"需求开始
- 从接收需求的第一刻起就要有需求池,不是开工才建。
- 大企业:需求工单,提出即有沟通记录;小企业:领导/同事随口一句,你必须自己去挖掘真实用途。
- 需求池是**多张表**:总表、在分析的、在开发的——分状态管理。
- 分析和排优先级这两个动作都发生在需求池里,不是拍脑袋。

### 2. 伪需求辨认:分析的本质是找到"真实需求"
- "分析需求"回答的唯一问题是:**真实需求是什么**。
- 提出者说的话 ≠ 需求本身;每个人表述的都是自己视角的方案,不是真需求。
- 伪需求是专门课题(导师建议自行搜索深挖)。

### 3. 前期学习法:模仿 → 对比 → 差异即提升点
- 找一个你想进入的行业,申请体验账户,把产品从头到尾用一遍,边用边截图。
- 用截图**逐个梳理功能点**,然后自己模仿着做一遍。
- **你的想法 vs 人家企业实际落地的差异,就是你要提升的点**——这是导师给的核心成长闭环。
- 产品能力 = 用出来的、抄出来的、踩坑踩出来的,并且要**记录**。

### 4. 需求功能脑图:先想清楚功能之间的依赖
- 进入设计前,先用功能脑图头脑风暴,理清**各功能点的关联**。
- ToB 场景尤其明显:**做或改一个功能,背后需要好多功能支撑**——依赖链必须先画出来。

### 5. 业务流程:把一个业务拆成阶段和规则
以"购买商品"为例,导师示范了拆解颗粒度:
- 前置:用户登录、绑银行卡、可抵扣的余额账户
- 过程:选商品 → 购买
- 规则:平台购买限制(同一商品可买多少)、库存抵扣逻辑、**什么时候扣库存**、付款方式组合
- 结果:先有购买单,最后有订单

→ 教训:规则和时序(如扣库存时机)必须在设计期就明确,不能留给开发现场决定。

### 6. 状态流转图:每个状态对象都要有"状态×条件×流转"
- 订单示例:新创建 / 待付款 / 已付款 / 已取消。
- 每个状态要写清:**触发条件、变化条件、怎么流转**。
- 再补上其他说明和规则。

### 7. 文档与图:文字是核心,图只是工具
- 原型图必须有图**也必须有说明**;**说得清楚才看得明白**。
- 常用图六种:流程图、泳道图、原型图、功能结构图、用例图、时序图。
  - 时序图对开发最友好,画简单些也能替代部分流程图。
- **图只是工具,核心是讲明白需求**——不追求图的规范华丽,追求表达完整。

### 8. 需求评审:对象、顺序、尺度
- 评审对象:业务、开发、运营。
- 顺序:**先业务后开发**——先确保业务功能满足,再过技术。
- 评审看四样东西:业务流程、文档、原型图、交互。
- **不要盲目听从任何一方;产品沟通的尺度很重要**——你是需求的最终责任人。
- 心理预期:评审完多半会改,会加、会删——这是常态不是失败。

### 9. 拆分交付:时间不够就抽核心
- 有些需求因为时间要拆开,把核心抽成一个先做(分阶段交付的雏形)。

### 10. 开发与测试:沟通要记录,用例要对齐
- 开发过程一定会冒出问题,沟通好之外还要**记录**。
- 需求评审时就要和测试沟通**测试用例**;有些用例产品自己写一份自用,测试用例等测试自己写(职责分界)。

### 11. 验收与迭代:以文档为契约
- 产品验收的标准 = 是否符合你的需求文档——文档是契约,不是形式。
- 上线前:开发打包 → 准备发布 → 上线 → 再走一遍流程验收测试(回归)。
- 使用中发现要优化/调整的,记录下来 → 就是下一轮迭代方向。

### 12. 心法与现实认知
- **产品就是踩坑、沟通。**
- **不要相信任何人,谁的话都会骗你——因为每个人思考不一样。**(不是恶意,是视角差异;所以文档、记录、对照验收才重要)
- 商业化/盈利:导师诚实声明这是他的短板(ToB 背景,只会按业务承接、合法合规、开发的思路走)——**盈利能力需要另找输入源**。
- 小企业现实:数据分析跟踪用得少,一般看业务订单做简单分析(导师的环境;对标大厂时此项需要额外补课)。
- 职场现实:进公司多数是接手旧系统,靠**大量使用**来建立熟练度。

### 附:AI 协作法(对独立开发者最重要的一条)
- 做功能落地/原型交互时:**先自己做出一个版本,再和 AI 沟通,看它的方向和结果**。
- 顺序不可反:先有自己的版本,AI 是校准器和陪练,不是替代你思考的起点。

## 三、一人全栈落地映射(把导师方法翻译成单人工作流)

一人公司 = 产品/开发/测试/运营四个角色合一,**流程不省略,角色自己轮着当**:

| 导师的方法 | 单人全栈的执行方式 |
| --- | --- |
| 需求池多张表 | 一个 Git 仓库的 issues 或一张多维表:inbox(总)/ analyzing / building 三列状态 |
| 伪需求辨认 | 每条需求写一句"真实用途是什么",写不出来就不开工 |
| 找体验账户梳理功能点 | 对标大厂产品:注册体验版,截图建"竞品功能清单",逐功能复刻 |
| 想法 vs 落地的差异 = 提升点 | 复刻后写差异复盘:哪些规则/边界人家做了我没做(尤其是限制、时序、异常路径) |
| 功能脑图理依赖 | 写码前先画功能脑图;ToB 式依赖链 = 前后端模块依赖清单 |
| 业务流程 + 状态流转图 | 直接映射为代码:状态机/枚举 + 流转守卫条件;扣库存时机这类规则落成显式常量和注释 |
| 先业务后开发的评审顺序 | 先写"业务验收标准"(用户视角,能跑通的剧本),再写技术方案 |
| 不要盲目听从谁 | 单人场景下"谁"= AI 的建议和用户的随口反馈:都要对照自己的验收标准 |
| 评审完会改会加会删 | 把"改/加/删"当常态:需求文档放仓库里版本化,不追求一次定稿 |
| 时间不够抽核心 | MVP 顺序:先抽核心闭环上线,其余进迭代池 |
| 和测试沟通用例 | 验收标准直接写成自动化测试;产品自用用例 = 冒烟测试清单 |
| 验收对照文档 | 文档里的每条规则都要有对应测试;上线前跑全量回归 |
| 记录优化点进迭代 | 线上问题/想法当天进需求池,不留在脑子里 |
| 先有版本再问 AI | 所有设计:先自己写一版文档/原型/方案,再让 AI 评审找漏,方向校准 |
| 产品就是踩坑沟通 | 踩坑必须记录(事故记录 + 经验变检查),沟通对象是用户和 AI,同样要留痕 |

**对标大厂的最短路径**(导师方法直接套用):
1. 选定行业 → 找该行业顶级产品 → 申请/注册体验账户
2. 全流程使用 + 截图 → 梳理出完整功能点清单(含边界规则:限购、扣库存时机、支付组合、状态流转)
3. 逐功能复刻 → 复刻后做差异分析 → 差异清单就是你的升级路线图
4. 盈利模式设计另找输入源(导师明确的盲区,可用商业模式画布/大厂财报拆解补)

## 四、每轮迭代检查清单

设计期:
- [ ] 真实需求一句话写清了吗(不是对方说的方案)?
- [ ] 功能脑图画了吗?依赖功能列全了吗?
- [ ] 核心业务流程的阶段和规则写了吗(限制、时序、组合)?
- [ ] 有状态的对象画状态流转图了吗(状态 × 触发条件 × 变化条件)?
- [ ] 原型有图也有文字说明吗?
- [ ] 本次迭代的范围从需求池里圈出来了吗?时间不够时核心抽出来了吗?
- [ ] 先自己有版本,然后才问的 AI?

评审期(自己对自己,或对 AI):
- [ ] 先过业务(用户剧本能跑通),再过技术?
- [ ] 业务流程、文档、原型、交互四样齐了吗?
- [ ] AI/用户的意见,有没有盲从?

开发期:
- [ ] 开发中发现的问题和决定,记录了吗?
- [ ] 文档里每条规则都有测试对应吗?

上线期:
- [ ] 按"验收标准 = 需求文档"逐条验收了吗?
- [ ] 回归测试跑了吗?
- [ ] 要优化/调整的点记进下一轮迭代池了吗?
