## 并行写入范围

- 集成人：contracts、生成配置、迁移、lockfile、根门禁。其他任务先提出契约变更，再开始依赖实现。
- 服务端任务：指定业务模块及其测试；不能顺手修改邻接模块实现。
- 前端任务：指定 feature、路由、页面状态与测试；共享组件/API client变更交集成人。
- 媒体/工作流任务：指定 activities/workflows；不能直接重写账本或绕过素材权限。
- 每个任务在独立 worktree 执行，集成人按契约先后顺序合入。没有负责人口令，不执行 Git commit。

## 第一个可靠纵向切片

一个用户提交一个5秒营销视频，拿到作业ID，worker执行可控供应商模拟，标识后得到可查询资产，账本只终结一次。这个切片同时检验身份、报价、任务、资产、模型适配、观测与前端客户端；失败路径必须先于规模扩展完成。

## 外部依赖和未决项

- 小程序认证、真实支付商户能力、域名/部署凭据沿用阻塞墙；开发无需生产密钥。
- 角色一致性方案尚未做真实模型spike，不能承诺只靠提示词即可跨集一致。
- Temporal部署形态、成本和恢复实证由R1.3输出；本地开发服务启动不等于生产就绪。
- 供应商是否支持受理幂等/查询需逐一验证；不支持时必须提供未知受理处置，而非自动重复扣费。
- AI绘画与漫剧定价没有本次新增商业授权，能力实现与收费开关分开验收，不从视觉稿推导收费规则。

## 首阶段验证入口

- `pnpm verify:isolated`：为旧系统建立可重复的隔离门禁基线；不是新系统完成证明。
- `pnpm audit:wallet`：仅接受显式指定的loopback审计库，检查3个已复现钱包不变量；旧实现预期退出1。
- 测试数量、失败数量、缓存命中和未覆盖范围需随实际运行更新，不能只写“已通过”。

2026-10-06实测：`pnpm verify:isolated --wallet-audit` → gate 29/29任务、0缓存，原54项测试+工具6项测试均无失败；随后3项钱包正确性检查全部失败，总退出1；`docker ps --all --filter label=wb.verify-run=<本次ID>`返回0容器。调整工具测试为直接执行`.test.mjs`后，`node scripts/verify-isolated.test.mjs`再次执行6项、失败0。未完成新业务实现、真实模型/支付、微信真机与迁移演练。
